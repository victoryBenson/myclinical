SUBJECT: Official Baseline Audit & Engineering Roadmap for Ithere Care

Ithere Care represents an ambitious, highly structured initiative to engineer an institutional-grade Hospital Information Management System. Over preceding development cycles, significant foundational engineering has been achieved: a robust NestJS 11 backend with 70+ endpoints, 35 normalized database tables, and an expansive 169-route frontend shell.

However, as development resumes, our audit has uncovered a critical operational divide: while the backend possesses fully implemented, tested business logic for Laboratory, Pharmacy, Appointments, and Billing, the frontend currently operates primarily on mock data files and UI staging templates.

This document establishes the official engineering baseline. We recommend resisting the temptation to rewrite working modules or blindly generate new UI screens. Instead, by executing the targeted 5-Phase Roadmap beginning with Sprint 1 (Appointments, Lab, and Pharmacy API Integration), the team will transform this sophisticated prototype into a commercially viable, end-to-end hospital management system.

Frontend Architectural Findings & Code Smells

FINDING FE-01 • HIGH SEVERITY
Appointment Code Duplication & Patient Collision
In src/pages/appointments/, four files (Home.tsx, CreateNewPatient.tsx, CreateOPDPatient.tsx, CreatePatientDashboard.tsx) are copy-pasted duplicates of the patient registration views. Furthermore, appointments/Home.tsx reads localStorage.getItem("patient-tab") and displays patient records instead of appointments. The backend /appointments API is completely bypassed.
FINDING FE-02 • HIGH SEVERITY
Competing State Management Patterns (Zustand vs. React Query)
The application suffers from dual state paradigms: features/hmo/useHmos.ts uses @tanstack/react-query, while store/patient.store.ts manually manages patients[], loading, and error in Zustand. This creates cache synchronization issues, stale data across tabs, and redundant network requests.
FINDING FE-03 • MEDIUM SEVERITY
Monolithic Route Bundling & Broken Internal Links
src/routes/AppRoutes.tsx statically imports all 169 components at the top of the file, forcing users to download all 13 directorates on initial load. In addition, navigation buttons in LabDashboard.tsx link to /pharmacy-diagnostics/lab-requests (which does not exist in AppRoutes.tsx), causing silent redirects to /login.

SECTION 07

Database Architecture & Referential Integrity

The database layer consists of 35 PostgreSQL tables hosted on Neon Serverless (AWS us-east-2). While the table structures cover the requisite healthcare entities, empirical inspection revealed critical relational inconsistencies that must be addressed.

Database Entity Relationship Diagram

Critical Database Weaknesses

DB-01 • HIGH RISK
Missing Foreign Keys on Clinical Records
patients.id is an auto-incrementing integer. However, appointments.patientId, clinical_encounters.patientId, lab_requests.patientId, and prescriptions.patientId are defined as character varying. Because of this type mismatch, no foreign keys exist to patients. Cascading deletes, updates, and relational integrity are completely unenforced.
DB-02 • HIGH RISK
Multi-Tenant organizationId Type Divergence
organizations.id is typed as uuid. However, patients.organizationId and staff.organizationId are typed as integer, while clinical tables use character varying. This makes multi-tenant partitioning fragile and blocks relational joins across organizational boundaries.

SECTION 10

Technical Debt, Risks & Architectural Recommendations

To ensure Ithere Care can evolve into a multi-hospital enterprise deployment without costly rewrites, technical debt accumulated during rapid prototyping must be systematically remediated.

DEBT-01 • HIGH PRIORITY
State Management Dualism
Issue: Mixing manual Zustand array manipulation with React Query.
Impact: Cache desynchronization, stale lists, duplicated network calls.
Mitigation: Enforce @tanstack/react-query for all server data caching; restrict Zustand strictly to user session, active tenant, and UI preferences.
DEBT-02 • HIGH PRIORITY
Database Foreign Key Gaps
Issue: patientId stored as varchar without foreign key constraints.
Impact: Data corruption, orphaned medical records, unable to perform relational cascades.
Mitigation: Execute a TypeORM migration altering clinical patientId columns to integer with foreign keys referencing patients(id) ON DELETE RESTRICT.
DEBT-03 • MEDIUM PRIORITY
Monolithic Route Loading
Issue: All 169 pages statically imported in AppRoutes.tsx.
Impact: Massive initial bundle size, slow first-contentful-paint (FCP).
Mitigation: Implement dynamic code-splitting via React.lazy() and <Suspense> grouped by hospital directorate.
DEBT-04 • HIGH PRIORITY
Frontend Testing Vacuum
Issue: Zero automated tests in myclinical/src.
Impact: High risk of regression when connecting live APIs.
Mitigation: Configure Vitest and React Testing Library in myclinical; require unit tests for authentication, patient registration, and appointment booking.
Architectural Recommendation: Retain the Modular Monolith
We strongly advise AGAINST breaking the backend into microservices at this stage. The current NestJS modular monolith is well-partitioned, easy to debug, deploys as a single unit, and provides transaction safety across clinical and billing events. Premature microservices would introduce unnecessary distributed systems complexity without commercial benefit.
